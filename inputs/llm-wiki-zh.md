# LLM Wiki

一种用 LLM 构建个人知识库的模式。

这是一个理念文件，设计为直接复制粘贴到你自己的 LLM Agent（如 OpenAI Codex、Claude Code、OpenCode/Pi 等）中使用。它的目标是传达核心思想，具体细节则由你的 Agent 与你协作构建。

## 核心思想

大多数人对 LLM 与文档结合的体验是 RAG（检索增强生成）：你上传一批文件，LLM 在查询时检索相关片段，然后生成答案。这种方式确实有效，但 LLM 每次回答问题时都要从零开始重新发现知识——没有积累。提一个需要综合五份文档才能回答的微妙问题，LLM 每次都得重新找到并拼凑相关片段。没有任何知识被沉淀下来。NotebookLM、ChatGPT 文件上传以及大多数 RAG 系统都是这样运作的。

这里的思路不同。LLM 不是在查询时才从原始文档中检索，而是**增量构建并维护一个持久化的 wiki**——一个结构化的、相互链接的 Markdown 文件集合，位于你和原始资料之间。当你添加新资料时，LLM 不只是为后续检索做索引，而是阅读它、提取关键信息，并将其整合到已有的 wiki 中——更新实体页面、修订主题摘要、标注新数据与旧结论的矛盾之处，强化或挑战不断演进的综合观点。知识被编译一次，然后*保持更新*，而不是每次查询时重新推导。

这就是关键区别：**wiki 是一个持久化、不断复利增长的产物。** 交叉引用已经存在，矛盾已经被标记，综合观点已经反映了你读过的一切。每添加一份资料、每提一个问题，wiki 都会变得更加丰富。

你几乎从不（或极少）亲自写 wiki——LLM 负责编写和维护全部内容。你负责资料筛选、探索方向和提出好问题。LLM 处理所有苦力活——摘要、交叉引用、归档和记账，这些是让知识库真正长期有用的基础工作。实践中，我通常一边开着 LLM Agent，一边开着 Obsidian。LLM 根据我们的对话进行编辑，我实时浏览结果——跟踪链接、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。

这种模式适用于很多场景，举几个例子：

- **个人成长**：追踪自己的目标、健康、心理、自我提升——归档日记条目、文章、播客笔记，逐步构建关于自己的结构化画像。
- **研究**：花数周或数月深入一个主题——阅读论文、文章、报告，增量构建一个带有演进论点的全面 wiki。
- **阅读一本书**：随读随归档每章内容，为角色、主题、情节线索及其关联建立页面。读完后你就有了一本丰富的伴读 wiki。想想粉丝 wiki，比如 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page)——数千个相互链接的页面覆盖角色、地点、事件、语言，由志愿者社区历经多年构建。你可以一边阅读一边个人构建类似的东西，LLM 负责所有交叉引用和维护。
- **企业/团队**：由 LLM 维护的内部 wiki，由 Slack 讨论串、会议转录、项目文档、客户通话记录推送更新。可以选择让人工参与审核更新。wiki 保持最新状态，因为 LLM 做了团队里没人愿意做的维护工作。
- **竞品分析、尽职调查、旅行规划、课程笔记、兴趣爱好深入研究**——任何你需要长期积累知识并希望它有组织而非散乱的场景。

## 架构

有三个层次：

**原始资料**——你精心筛选的资料文档集合。文章、论文、图片、数据文件。这些是不可变的——LLM 从中读取但绝不修改。这是你的事实来源。

**Wiki**——一个由 LLM 生成的 Markdown 文件目录。摘要、实体页面、概念页面、对比分析、总览、综合论述。LLM 完全拥有这一层。它创建页面、在新资料到来时更新页面、维护交叉引用、保持一切一致性。你负责阅读，LLM 负责编写。

**模式（Schema）**——一个文档（如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM wiki 的结构是怎样的、遵循什么规范、以及在录入资料、回答问题或维护 wiki 时应遵循什么工作流。这是关键配置文件——正是它让 LLM 成为一个有纪律的 wiki 维护者，而非通用聊天机器人。你和 LLM 在逐步摸索出适合你领域的方法的过程中共同演进这个文件。

## 操作方式

**录入。** 你把一份新资料放入原始资料库，然后告诉 LLM 处理它。一个示例流程：LLM 阅读资料、与你讨论关键要点、在 wiki 中写入摘要页面、更新索引、更新整个 wiki 中相关的实体和概念页面、在日志中追加一条记录。一份资料可能触及 10-15 个 wiki 页面。我个人偏好逐份录入并保持参与——阅读摘要、检查更新、引导 LLM 把握重点。但你也可以在较少监督下批量录入多份资料。如何开发适合你风格的工作流，并将其记录在模式文件中以便后续会话使用，这取决于你。

**查询。** 你针对 wiki 提问。LLM 搜索相关页面、阅读它们、整合出带引用的答案。根据问题类型，答案可以采取不同形式——Markdown 页面、对比表格、幻灯片（Marp）、图表（matplotlib）、画布。重要洞察：**好的答案可以被归档回 wiki 作为新页面。** 你要求的一次对比、一篇分析、一个你发现的关联——这些都有价值，不应该消失在聊天记录里。这样一来，你的探索也像录入的资料一样，在知识库中产生复利效应。

**检查。** 定期让 LLM 对 wiki 进行健康检查。查找：页面之间的矛盾、已被更新资料推翻的过时论述、没有任何入站链接的孤立页面、被提及但缺少独立页面的重要概念、遗漏的交叉引用、可以通过网络搜索填补的数据空白。LLM 擅长建议需要调查的新问题以及需要寻找的新资料。这能保持 wiki 在不断增长中仍然健康。

## 索引与日志

两个特殊文件帮助 LLM（和你）在 wiki 增长时导航。它们各有不同用途：

**index.md** 是内容导向的。它是 wiki 中所有内容的目录——每个页面都列有链接、一行摘要，可选地包含日期或资料数量等元数据。按类别组织（实体、概念、资料等）。LLM 在每次录入时更新它。回答查询时，LLM 先读取索引找到相关页面，然后深入阅读。在中等规模下（约 100 份资料、数百个页面）效果出奇地好，避免了嵌入式 RAG 基础设施的需求。

**log.md** 是时间导向的。它是一份只追加的记录，记载了什么在何时发生——录入、查询、检查过程。一个有用的技巧：如果每条记录以一致的前缀开头（如 `## [2026-04-02] ingest | 文章标题`），日志就能用简单的 Unix 工具解析——`grep "^## \[" log.md | tail -5` 就能给出最近 5 条记录。日志为你提供了 wiki 演进的时间线，也帮助 LLM 了解最近完成了什么。

## 可选：CLI 工具

到了一定阶段，你可能会想构建一些帮助 LLM 更高效操作 wiki 的小工具。最显而易见的是 wiki 页面的搜索引擎——小规模时索引文件就足够了，但随着 wiki 增长，你会需要真正的搜索。[qmd](https://github.com/tobi/qmd) 是一个不错的选择：它是一个本地 Markdown 文件搜索引擎，具备混合 BM25/向量搜索和 LLM 重排序能力，全部在设备端运行。它同时提供 CLI 接口（LLM 可以通过 shell 调用）和 MCP 服务器（LLM 可以作为原生工具使用）。你也可以自己构建更简单的东西——LLM 可以在需求出现时帮你快速写一个简易搜索脚本。

## 技巧与小贴士

- **Obsidian Web Clipper** 是一个浏览器扩展，能将网页文章转换为 Markdown。对于快速将资料纳入原始资料库非常有用。
- **将图片下载到本地。** 在 Obsidian 设置 → 文件和链接中，将"附件文件夹路径"设为一个固定目录（如 `raw/assets/`）。然后在设置 → 快捷键中搜索"下载"，找到"下载当前文件的附件"并绑定快捷键（如 Ctrl+Shift+D）。剪辑文章后按下快捷键，所有图片就会下载到本地磁盘。这是可选的但很有用——它让 LLM 能够直接查看和引用图片，而不是依赖可能失效的 URL。注意，LLM 目前无法一次性原生读取含有内嵌图片的 Markdown——折中方案是先让 LLM 读文字，再单独查看部分或全部引用的图片以获取额外上下文。有点笨拙，但效果还不错。
- **Obsidian 图谱视图**是查看 wiki 整体形态的最佳方式——什么连接着什么，哪些页面是枢纽，哪些是孤岛。
- **Marp** 是一种基于 Markdown 的幻灯片格式。Obsidian 有对应插件。适合直接从 wiki 内容生成演示文稿。
- **Dataview** 是一个 Obsidian 插件，能对页面 frontmatter 执行查询。如果你的 LLM 为 wiki 页面添加 YAML frontmatter（标签、日期、资料数量），Dataview 可以生成动态表格和列表。
- wiki 不过是一个 Markdown 文件的 git 仓库。你免费获得版本历史、分支和协作能力。

## 为什么这套模式有效

维护知识库最繁琐的部分不是阅读或思考——而是记账。更新交叉引用、保持摘要最新、标注新数据与旧结论的矛盾、维持数十个页面之间的一致性。人类会放弃 wiki，因为维护负担的增长速度超过了其产生的价值。LLM 不会厌烦、不会忘记更新某个交叉引用、可以一次性触及 15 个文件。wiki 保持维护状态，因为维护成本几乎为零。

人的工作是筛选资料、指导分析方向、提出好问题、思考这一切意味着什么。LLM 的工作是除此之外的一切。

这个理念在精神上与 Vannevar Bush 的 Memex（1945）有共鸣——一个私人的、精心策划的知识存储，文档之间有联想轨迹。Bush 的设想比后来互联网的实际形态更接近这种模式：私有的、主动策划的，文档之间的连接与文档本身同等珍贵。他没有解决的部分是谁来做维护。LLM 接手了这件事。

## 说明

本文档有意保持抽象。它描述的是理念，而非具体实现。确切的目录结构、模式规范、页面格式、工具选择——所有这些都取决于你的领域、偏好以及你选择的 LLM。上面提到的所有内容都是可选且模块化的——选取有用的，忽略不需要的。例如：你的资料可能只有纯文本，那就完全不需要图片处理功能。你的 wiki 可能足够小，索引文件就是全部所需，不需要搜索引擎。你可能不关心幻灯片，只需要 Markdown 页面。你可能想要完全不同的输出格式组合。正确使用本文的方式是与你的 LLM Agent 分享它，然后一起协作实例化一个适合你需求的版本。本文档唯一的职责是传达这种模式。你的 LLM 可以搞定其余部分。
